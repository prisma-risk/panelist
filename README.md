# Panelist

Panelist is a Rust library for writing Grafana dashboards as concise, strongly
typed code.

```rust
use panelist::prelude::*;

let dashboard = dashboard! {
    title: "Service health";
    refresh: "30s";

    row "Traffic" {
        timeseries "Requests" {
            query: promql!("sum(rate(requests_total[$__rate_interval]))");
            unit: reqps;
            width: 12;
        }

        stat "Errors" {
            query: promql!("sum(rate(errors_total[$__rate_interval]))");
            unit: reqps;
            width: 12;
        }
    }
};

dashboard.validate()?;
dashboard.write_json("service.json")?;
# Ok::<(), panelist::Error>(())
```

Panel IDs, query reference IDs, and 24-column grid positions are assigned
automatically and deterministically. The resulting JSON is stable enough to
review in Git and close to Grafana's native dashboard model.

[![A Panelist dashboard rendered by Grafana](https://raw.githubusercontent.com/prisma-risk/panelist/main/examples/images/route_performance.png)](examples/README.md)

That screenshot is not a mockup. It is Grafana 13 rendering the output of
[`route_performance.rs`](crates/panelist/examples/route_performance.rs), which
is regenerated by `make render-examples`. See [the example
gallery](examples/README.md) for all six, or run `make demo` to click through
them on a live Grafana.

## Status

Panelist is under active development. Add the current release from crates.io:

```toml
[dependencies]
panelist = "0.3.0"
```

The minimum supported Rust version is 1.96. Panelist uses Rust 2024 and has no
async runtime or network client dependency.

## Macro DSL

The macro translates a small amount of syntax into ordinary typed builders. It
does not add loops, conditions, interpolation, or its own composition language:
Rust remains the composition language.

```rust
use panelist::prelude::*;

let dashboard = dashboard! {
    title: "API";
    uid: "api";
    description: "API health and performance.";
    tags: ["api", "production"];
    refresh: "30s";
    datasource: prometheus("prometheus-main");

    variable "instance" {
        query: promql!("label_values(up{job=\"api\"}, instance)");
        multi: true;
        include_all: true;
    }

    row "Latency" {
        timeseries "Request latency" {
            query: promql!("histogram_quantile(0.99, rate(request_duration_seconds_bucket[$__rate_interval]))") {
                legend_format: "p99";
            }
            unit: seconds;
            width: 12;

            legend {
                position: bottom;
                mode: table;
                values: [last, min, max];
            }
        }
    }
};
# let _ = dashboard;
```

The DSL supports `timeseries`, `stat`, `gauge`, `table`, `text`, `bar_gauge`,
and `heatmap` panels at both dashboard and row level. `promql!` and `loki!`
create typed query builders rather than opaque JSON values.

Dashboard links, cursor sync, and the full variable surface are reachable
too:

```rust
use panelist::prelude::*;

let dashboard = dashboard! {
    title: "API";
    cursor_sync: crosshair;

    link "Runbook" => "https://runbook.internal/api" {
        target_blank: true;
        tags: ["ops"];
    }

    variable "instance" {
        query: promql!("label_values(up, instance)");
        regex: "prod-.*";
        sort: alphabetical_asc;
        all_value: ".*";
        allow_custom_value: true;
        skip_url_sync: true;
        current "Production" => "prod";
    }
};
# let _ = dashboard;
```

A variable's kind comes from its selector: `query:`, `plugin:`, `value:`, or
`values:`. `plugin:` makes a datasource variable, and is distinct from
`datasource:`, which sets the datasource a *query* variable runs against:

```rust
use panelist::prelude::*;

let dashboard = dashboard! {
    title: "API";

    variable "source" {
        plugin: "prometheus";
        regex: "prod-.*";
        current "Main" => "prometheus-main";
    }

    variable "instance" {
        query: promql!("label_values(up, instance)");
        datasource: prometheus("prometheus-main");
    }
};
# let _ = dashboard;
```

Setting no selector, or more than one, is a validation error rather than a
guess. So is an option the chosen kind has no Grafana key for.

`regex` and `sort` have no Grafana key on a custom or constant variable.
Setting them there is a validation error rather than a silent no-op, because
an ignored `sort` and a working one look identical in the emitted JSON.

Every typed panel option is reachable from the DSL. There is no option that
requires dropping to `option "key": json!(…)`:

```rust
use panelist::prelude::*;

let dashboard = dashboard! {
    title: "Options";
    datasource: prometheus("prometheus-main");

    timeseries "Latency" {
        query: promql!("latency");
        fill_opacity: 30.0;
        line_width: 2.0;
        line_interpolation: smooth;
        show_points: never;
        span_nulls: true;

        tooltip {
            mode: multi;
            sort: desc;
        }
    }

    stat "Status" {
        query: promql!("up");
        color_mode: background;
        color: fixed(red);

        mapping "0" => "Down";
        mapping "1" => "Up" { color: green; }

        link "Runbook" => "https://runbook.internal/api" {
            target_blank: true;
        }

        reduce {
            calculations: [mean, max];
            fields: "/.*/";
        }
    }
};
# let _ = dashboard;
```

`color_mode` is shared between stat and heatmap panels and takes a different
vocabulary on each — `value`/`background`/`none` versus `scheme`/`opacity`.
The two sets are disjoint, so the right one is selected by what you write, and
pairing a panel kind with the wrong vocabulary is a compile error.

Table panels can transform, sort, and style their columns without leaving
the DSL:

```rust
use panelist::prelude::*;

let dashboard = dashboard! {
    title: "Routes";
    datasource: prometheus("prometheus-main");

    row "Routes" {
        table "Route performance" {
            query: promql!("sum by (route) (rate(http_requests_total[$__rate_interval]))") {
                ref_id: "A";
                format: table;
                instant: true;
            }
            width: 24;

            transform organize {
                rename "Value #A" => "RPS";
                order ["route", "RPS"];
            }
            sort_by: ("RPS", desc);

            override field("RPS") {
                unit: reqps;
                cell: colored_background;
            }
        }
    }
};
# let _ = dashboard;
```

Table configuration stays typed throughout:

- Transformations: `join_by_field`, `sort_by`, `organize`,
  `time_series_to_table`, and `labels_to_fields`. Scope any of them to one
  query with `only ref_id(..)`.
- Field matchers: `field(name)`, `regex(pattern)`, `type(field_type)`,
  `query(ref_id)`, `names([..])`, `numeric`, and `time`.
- Cell renderers: `auto`, `colored_text`, `colored_background`, `gauge`, and
  `sparkline`. Renderers with their own options also have block forms.

Set a default renderer with `cell: <type>;` on the table, or set one inside an
`override` for selected fields. For transformations Panelist does not model,
`transform: <expr>;` accepts a `RawTransformation` or `Transformation` value.

The most common multi-query table, one row per label value and one column per query, has its own builder. `keyed` turns a configured table into a `KeyedTable`, and each `Column` names its header once:

```rust
use panelist::prelude::*;

let routes = Table::new("Route performance")
    .width(24)
    .sort_by("p95", SortDirection::Descending)
    .keyed("route")
    .key_name("Route")
    .column(
        Column::new("RPS", promql!("sum by (route) (rate(http_requests_total[$__rate_interval]))"))
            .unit(Unit::RequestsPerSecond),
    )
    .column(
        Column::new("p95", promql!("histogram_quantile(0.95, sum by (route, le) (rate(http_request_duration_seconds_bucket[$__rate_interval])))"))
            .unit(Unit::Seconds)
            .cell(TableCellType::ColoredBackground)
            .thresholds(Thresholds::new().green(0.0).yellow(0.3).red(1.0)),
    )
    .column(
        Column::trend("Trend", promql!("sum by (route) (rate(http_requests_total[$__rate_interval]))"), Reducer::Last)
            .cell(SparklineCell::new().hide_value(true)),
    );

let dashboard = Dashboard::new("Routes")
    .datasource(prometheus("prometheus-main"))
    .row(Row::new("Routes").panel(routes));
# let _ = dashboard;
```

It lowers into the ordinary table you would otherwise write by hand: instant `format: table` queries for value columns and a range query for each trend, reference IDs, a time-series-to-table step for the trends, an outer join on the key, an organize step that renames Grafana's `Value #<refId>` and `Trend #<refId>` fields to the column names and orders them, and one override per column. Anything set on the table before `keyed` comes after the lowering, so extra overrides win and extra transformations see the column names. The join is Grafana's plain outer join: the tabular outer join expands into one row per key per query on Grafana 11.5. A key is one label, because Grafana joins on one field; build a combined label with PromQL's `label_join` to key on several. The `dashboard!` macro has no keyed-table syntax yet, so add a keyed table to a row with `panels: [..];`.

Heatmap panels configure their color scale and Y axis directly:

```rust
use panelist::prelude::*;

let dashboard = dashboard! {
    title: "Latency";
    datasource: prometheus("prometheus-main");

    row "Latency" {
        heatmap "Latency distribution" {
            query: promql!("sum by (le) (rate(request_duration_seconds_bucket[$__rate_interval]))") {
                format: heatmap;
            }
            unit: seconds;
            width: 12;
            color_scheme: "Oranges";
            color_steps: 64;
            cell_gap: 1;
            calculate: false;

            y_axis {
                unit: seconds;
                placement: left;
            }
        }
    }
};
# let _ = dashboard;
```

Repeats, time overrides, value mappings, data links, and annotations are one line each:

```rust
use panelist::prelude::*;

let dashboard = dashboard! {
    title: "API";
    datasource: prometheus("prometheus-main");

    variable "instance" {
        query: promql!("label_values(up{job=\"api\"}, instance)");
        multi: true;
    }

    annotation "Restarts" => "changes(process_start_time_seconds{job=\"api\"}[2m]) > 0" {
        text_format: "{{instance}} restarted";
        icon_color: orange;
    }

    stat "Up on $instance" {
        query: promql!("up{instance=\"$instance\"}");
        repeat: horizontal("instance", 4);
        time_from: "1h";
        min_interval: "30s";

        mapping "1" => "Up" { color: green; }
        mapping range(0.0, 0.5) => "Degraded" { color: yellow; }
        mapping special(null) => "No data";

        link "Runbook" => "https://runbook.example/api";
        data_link "Logs" => "/explore?instance=${__field.labels.instance}" {
            keep_time: true;
        }
    }
};
# let _ = dashboard;
```

Grafana expands a repeat when the dashboard loads, so Panelist lays out the authored panel once. A horizontal repeat always spans the full row, because Grafana stretches it to 24 columns and splits that row between the clones, `max_per_row` at a time (4 by default). A vertical repeat keeps the panel's width. `Row::repeat` repeats a whole row. Repeating by a variable the dashboard does not declare is a validation error.

Value mappings come in Grafana's four kinds: exact `value`, numeric `range`, `regex`, and `special` (null, NaN, null or NaN, true, false, empty). Panelist emits them the way Grafana's mapping editor saves them, so exact values take precedence over the other kinds. `link` adds a link to the panel header and `data_link` adds one to the field values; both are Grafana data links, and `DataLinkVariable` spells the built-in `${__value.raw}`-style variables. `annotation` adds a typed Prometheus annotation query, and `RawAnnotation` covers other datasources.

## Builder API

Every important DSL construct has a normal Rust equivalent for IDE discovery,
dynamic generation, and users who prefer builders:

```rust
use panelist::prelude::*;

let panel = Timeseries::new("Requests")
    .query(
        PrometheusQuery::new("rate(http_requests_total[$__rate_interval])")
            .legend_format("{{status}}"),
    )
    .unit(Unit::RequestsPerSecond)
    .width(12);

let dashboard = Dashboard::new("HTTP")
    .datasource(prometheus("prometheus-main"))
    .row(Row::new("Traffic").panel(panel));
# let _ = dashboard;
```

The typed API covers:

- dashboards, rows, datasources, time ranges, links, and persisted variable
  state;
- Prometheus and Loki queries, including time-series, table, and heatmap
  result formats;
- datasource, query, custom, and constant variables;
- field defaults, value, range, regex, and special value mappings, field data links, thresholds, legends, overrides, and field matchers;
- panel repeats, row repeats, query options, and relative time overrides;
- Prometheus annotation queries and Grafana's built-in annotation entry;
- transformations, keyed multi-query tables, table cells and sorting, heatmaps, and the common options for stat, time-series, gauge, and bar-gauge panels.

When Grafana supports something Panelist does not model yet, use `RawQuery`,
`RawPanel`, `RawTransformation`, or the ordered `extra`, `option`, and `custom`
methods.

Real-world provisioning metadata and visualization choices remain typed:

```rust
use panelist::prelude::*;

let dashboard = Dashboard::new("Operations")
    .target(GrafanaTarget::V11_5)
    .version(1)
    .cursor_sync(DashboardCursorSync::Crosshair)
    .variable(
        DataSourceVariable::new("datasource", "prometheus")
            .current(VariableSelection::new("staging", "prometheus-staging")),
    )
    .panel(
        Timeseries::new("Requests")
            .query(
                PrometheusQuery::new("sum(rate(requests_total[5m]))")
                    .editor_mode(QueryEditorMode::Code),
            )
            .fill_opacity(10.0)
            .show_points(PointVisibility::Never)
            .tooltip(Tooltip::new().mode(TooltipMode::Multi)),
    );
# let _ = dashboard;
```

## Automatic layout

Grafana dashboards use 24 columns. Panelist places panels from left to right,
wraps before a panel would exceed column 24, and advances following rows below
the tallest panel on each line. Defaults are visualization-specific; use
`.width()`, `.height()`, or `width:`/`height:` in the DSL to adjust them.

An explicit `GridPos` remains available for unusual layouts:

```rust
# use panelist::prelude::*;
let panel = Timeseries::new("Pinned")
    .grid_pos(GridPos::new(6, 10, 12, 8));
# let _ = panel;
```

Expanded rows serialize their panels at the dashboard level, as Grafana Classic
expects. Collapsed rows retain their panels inside the row object and only
consume the one-unit row header while collapsed.

### Panel IDs

By default, panels and rows are numbered `1, 2, 3, …` in dashboard order, skipping any ID pinned with `.id(N)`. These positional IDs are small and readable, but inserting or reordering a panel renumbers everything after it. That breaks `viewPanel=` and `editPanel=` links and embeds, and makes every later panel show up in the JSON diff.

`PanelIds::Stable` derives each ID from the panel's identity instead, so it survives insertion, removal, reordering, and collapsing a row:

```rust
use panelist::prelude::*;

let dashboard = Dashboard::new("Checkout")
    .panel_ids(PanelIds::Stable)
    .row(
        Row::new("HTTP")
            .key("http")
            .panel(Timeseries::new("Requests"))
            .panel(Stat::new("Errors").key("errors")),
    );
# let _ = dashboard;
```

An unkeyed panel's identity is its row's identity plus its own title, and a row's identity is its title. So renaming an unkeyed panel, or the row it sits in, changes its ID. A `.key("…")` replaces the titles: a keyed row keeps its ID, and its unkeyed panels keep theirs, across a rename, and a keyed panel keeps its ID across a rename and a move to another row. Use keys where titles repeat or where links must outlive a rename.

The hash is a fixed, documented FNV-1a, so IDs never change between Rust or Panelist releases, and they fall in `65536..2^30`, inside Grafana's `uint32` panel IDs and clear of small hand-pinned IDs. Two panels or rows that land on the same ID, including a derived ID equal to an explicit one, are a validation error naming both. Panelist never quietly picks another ID.

## Reusable components

Fragments are ordinary Rust values:

```rust
use panelist::prelude::*;

fn http_panels(service: &str) -> Vec<Panel> {
    vec![
        Timeseries::new("Requests")
            .query(PrometheusQuery::new(format!(
                "sum(rate({service}_requests_total[$__rate_interval]))"
            )))
            .into(),
        Stat::new("Errors")
            .query(PrometheusQuery::new(format!(
                "sum(rate({service}_errors_total[$__rate_interval]))"
            )))
            .into(),
    ]
}

let panels = http_panels("checkout");
let dashboard = dashboard! {
    title: "Checkout";
    row "HTTP" {
        panels: panels;
    }
};
# let _ = dashboard;
```

## Serialization and validation

`Dashboard` implements `serde::Serialize`, so normal `serde_json` APIs work.
The convenience methods add structured errors and file output:

```rust
# use panelist::prelude::*;
# let dashboard = Dashboard::new("Example");
dashboard.validate()?;
let compact = dashboard.to_json()?;
let pretty = dashboard.to_json_pretty()?;
dashboard.write_json("dashboard.json")?;
# let _ = (compact, pretty);
# Ok::<(), panelist::Error>(())
```

Validation reports duplicate explicit panel IDs and query refs, stable panel ID collisions, dashboard UIDs Grafana would refuse, missing titles or expressions, invalid widths and positions, zero heights, and malformed threshold ordering. Invalid authored dashboards return errors instead of panicking.

It also rejects repeats by undeclared variables, malformed minimum intervals and time overrides, value mappings that can never match or change nothing, duplicate exact-value mappings, and annotations without a name or expression.

## Rendering a directory

Dashboards as code usually means committing the generated JSON, so reviewers see the wire diff and Grafana can provision the files. `DashboardSet` writes a set of dashboards into a directory and checks that directory in CI:

```rust,no_run
use std::process::ExitCode;

use panelist::prelude::*;
use panelist::DashboardSet;

fn main() -> ExitCode {
    let dashboards = DashboardSet::new()
        .dashboard(Dashboard::new("Checkout").uid("checkout"))
        .dashboard(Dashboard::new("Payments").uid("payments"));

    let result = if std::env::args().any(|arg| arg == "--check") {
        dashboards.check_dir("dashboards")
    } else {
        dashboards.write_dir("dashboards").map(drop)
    };
    match result {
        Ok(()) => ExitCode::SUCCESS,
        Err(error) => {
            eprintln!("{error}");
            ExitCode::FAILURE
        }
    }
}
```

Each dashboard becomes `<uid>.json`: validated, pretty-printed JSON with a trailing newline. A dashboard without a UID, or two dashboards sharing one (ignoring case, for case-insensitive filesystems), is an error. `check_dir` never writes; it fails with a report listing every stale file, every missing file, and every orphaned `.json` file that no dashboard renders to anymore. `write_dir` removes the orphans, rewrites only files whose contents changed, and replaces each file atomically. Other files in the directory are left alone.

### Variable references

Validation also checks that every template variable a dashboard references is declared. Grafana leaves an unresolved reference in place, so a typo like `$enviroment` reaches the datasource verbatim and the panel just shows no data. Panelist reports it as `ValidationError::UnknownVariableReference`, naming the dashboard, panel or variable, the field, and the name.

These fields are scanned:

- query expressions and legend formats
- datasource UIDs on the dashboard, panels, queries and query variables, such as `prometheus("$datasource")`
- dashboard and panel link URLs
- query variable definitions

All of Grafana's syntaxes are recognised: `$name`, `${name}`, `${name:format}`, `${name.path}`, `[[name]]` and `[[name:format]]`. Matching follows Grafana's own pattern, so `$env_name` is one variable called `env_name`, not `$env` followed by `_name`. Write `${env}_name` for the latter.

Grafana's global variables need no declaration: `$__rate_interval`, `$__interval`, `$__interval_ms`, `$__range`, `$__range_s`, `$__range_ms`, `$__rate_interval_ms`, `$__from`, `$__to`, `$__timeFilter`, `$timeFilter`, `$__timezone`, `$__dashboard`, `$__name`, `$__org`, `$__user`, `$__url_time_range`, `$__all_variables`, `$__all`, `$__auto` and `$__searchFilter`. Dotted forms like `${__user.login}` resolve through their base name. A misspelt built-in in a Prometheus or Loki query is still an error. A `RawQuery` targets a plugin Panelist does not know, so it also accepts any name in Grafana's reserved `__` namespace, such as the SQL macros `$__timeGroup` and `$__unixEpochFilter`, plus InfluxQL's legacy `$interval`.

Grafana resolves variables in declaration order. A chained query variable may only reference variables declared before it, in its query or its datasource. A query variable that inherits the dashboard datasource needs that datasource's variable declared first too. Breaking the order is a `ValidationError::VariableReferencedBeforeDeclaration`. Panels resolve after every variable, so order does not matter to them.

Some `$` signs are not references and never trip the check. Variable `regex` options are not scanned, so anchors like `/^(prod|staging)$/` are fine. Capture references like `$1` and `${1}` in `label_replace` are ignored, because no variable can have an all-digit name. A `$` followed by no name, as in `"^api$"`, starts no reference.

## Grafana compatibility

Panelist emits Grafana Classic dashboard JSON. Classic remains importable and exportable in Grafana 13, works with file provisioning, and retains the numeric panel IDs and `gridPos` behavior that Panelist automates. Grafana's newer V2 resource model uses a different layout representation.

A `GrafanaTarget` names the Grafana release line the JSON is written for. It sets `schemaVersion` to the version that release considers current, so Grafana runs no migration over the dashboard on load and its export matches the committed file:

| Target | Verified against | `schemaVersion` |
| --- | --- | --- |
| `GrafanaTarget::V11_5` | Grafana 11.5.2 | 40 |
| `GrafanaTarget::V13` (default) | Grafana 13.0.2 | 42 |

```rust
# use panelist::prelude::*;
let dashboard = Dashboard::new("Checkout").target(GrafanaTarget::V11_5);
# let _ = dashboard;
```

`make verify-grafana` round-trips every golden dashboard, rendered for each target, through that target's Grafana release and fails if Grafana drops or alters any property. For another release, pick the nearest older target and override the number with `.schema_version(N)`; that changes only the number.

The authoring model, layout/normalization pass, and Grafana serialization model
are separate modules so a future V2 serializer can preserve the DSL and
builders. See [the schema strategy](https://github.com/prisma-risk/panelist/blob/main/docs/schema-compatibility.md)
for scope and references.

## Examples

Six runnable examples live in [`crates/panelist/examples`](crates/panelist/examples),
and each one prints its dashboard JSON:

```bash
cargo run -p panelist --example basic
```

- [`basic.rs`](crates/panelist/examples/basic.rs) — smallest useful dashboard
- [`prometheus.rs`](crates/panelist/examples/prometheus.rs) — multiple targets,
  thresholds, overrides, and legend calculations
- [`variables.rs`](crates/panelist/examples/variables.rs) — query and custom
  variables
- [`layout.rs`](crates/panelist/examples/layout.rs) — automatic wrapping and a
  reusable Rust fragment
- [`full_dashboard.rs`](crates/panelist/examples/full_dashboard.rs) — realistic
  GeoIP dashboard using Prometheus and Loki
- [`route_performance.rs`](crates/panelist/examples/route_performance.rs) — operational dashboard exercising a keyed multi-query table, typed table cells and sorting, Prometheus result formats, and heatmap options, with zero escape hatches

[The gallery](examples/README.md) shows what each one looks like once Grafana
has rendered it. `make demo` boots Prometheus, Loki, and Grafana in Docker,
provisions all six from the examples themselves, and serves them on
<http://localhost:3000>; `make render-examples` regenerates the gallery
screenshots from that stack, so an image cannot drift from its example.

## Roadmap

- Wire `scripts/verify-grafana.sh` (`make verify-grafana`) into CI so every change is validated against a live Grafana for every target automatically. The check already round-trips every golden through Grafana 11.5.2 and 13.0.2 cleanly; it just isn't triggered on every push yet.
- Add targets for the Grafana releases in between (11.6 through 12.1 use `schemaVersion` 41) once each has a verified golden round trip.
- Add an opt-in Grafana V2 resource serializer and dynamic layouts.
- Add more transformation types beyond the five modeled today (join, sort, organize, time-series-to-table, labels-to-fields).
- Add more datasource query types without turning the core crate into an API
  client.
- Stabilize the API from real-world dashboard authoring feedback.
